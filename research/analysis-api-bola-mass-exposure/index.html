Massive PII & Administrative Data Leak via API BOLA

DATE: 2026-09-04 SEVERITY: CRITICAL CATEGORY: BOLA / DATA_EXPOSURE

EXECUTIVE SUMMARY

This analysis documents a Broken Object Level Authorization (BOLA) vulnerability on the DevSphere platform. By manually manipulating API endpoints from singular resources to plural collections, an unprivileged user can exfiltrate the entire user database, including private emails, internal roles, and PBKDF2 password hashes for all accounts, including System Administrators.

EXPLOITATION_POC (VIDEO)

TECHNICAL_WALKTHROUGH

The exploitation sequence moves from standard enumeration to manual logic testing of the API structure.

1. Discovery via Fuzzing

Using ffuf, I identified the standard endpoint used by the application to manage individual profile data: /api/v1/user.

DIRECTORY_FUZZING_CLI
ffuf -u http://127.0.0.1:5000/FUZZ -w ./api_wordlist.txt -b "session=[USER_COOKIE]"

[+] /api/v1/user  [Status: 200, Size: 121]

2. Manual API Pluralization Test

Based on the discovery of the singular resource, I conducted a manual test using the pluralized version of the endpoint (/users). The backend failed to implement any authorization checks on this collection-based resource.

MANUAL_ENDPOINT_MANIPULATION
# Requesting the pluralized collection endpoint
curl -s http://127.0.0.1:5000/api/v1/users -b "session=eyJ1c2Vy..." | jq .

3. Mass Data Exfiltration

The server responded with a massive JSON array containing the full database records of every user registered on the platform. The data was not filtered, exposing password hashes and administrative roles.

Impact Analysis: This vulnerability represents a complete failure of the platform's authorization model. Access to administrator password hashes allows for infrastructure-wide compromise, while the leak of thousands of user emails constitutes a major privacy violation.

REMEDIATION_STRATEGY

To mitigate this, the application must enforce strict Object-Level Authorization. Access to collection endpoints like /api/v1/users must be restricted solely to users with SYSTEM_ADMIN privileges. Furthermore, sensitive security fields such as password hashes should never be returned in any public-facing API response.
