Information Disclosure via Client-Side Filtering

DATE: 2026-08-01 SEVERITY: MEDIUM CATEGORY: SENSITIVE_DATA_EXPOSURE

EXECUTIVE SUMMARY

This analysis investigates an Information Disclosure vulnerability on the CivicEcho Portal. The system is designed to display only a user's own complaints. However, the server-side implementation fetches every record from the database and relies on CSS-based Client-Side Filtering (display: none) to hide unauthorized reports. This allows any authenticated user to view private citizen grievances by simply inspecting the HTML source code.

EXPLOITATION_POC (VIDEO)

TECHNICAL_WALKTHROUGH

The vulnerability was discovered by analyzing the underlying HTML source code of the user dashboard after submitting a legitimate complaint.

1. Baseline Activity: An account was registered as test@example.com. A complaint with the subject "test" and content "test" was submitted.

2. Discovery: Upon navigating to the dashboard, the UI correctly showed only the "test" report (Tracking ID: CE-9E4A). However, by performing a View Page Source (Ctrl+U), the full data set of all citizen reports was found to be present in the raw HTML response.

HTML_SOURCE_VIEW_LEAK
<!-- Hidden Report (Belongs to another user) -->
<div class="case-card shadow-sm restricted-data">
    <span class="fw-bold">CE-99281 &mdash; Bridge damage in West Sector</span>
    <p>The main bridge connecting sector 4 and 5 has visible cracks...</p>
    <p>Official Response: Engineering team dispatched for structural assessment.</p>
</div>

<!-- My Legitimate Report -->
<div class="case-card shadow-sm">
    <span class="fw-bold">CE-9E4A &mdash; test</span>
    <p>test</p>
</div>

3. Impact Analysis: The server utilizes the .restricted-data { display: none; } class to obscure elements visually. While this effectively hides the content in the rendered browser view, the Tracking ID, Subject, Full Content, and Official Government Notes of other citizens are fully exposed to anyone who can view the page source.

REMEDIATION_STRATEGY

To mitigate this attack, it is recommended to implement Server-Side Filtering. The database query should be restricted to fetch only the records associated with the current session's user_id. Sensitive data should never reach the client's browser if they are not authorized to view it.
